# Code Review Red Flags

This document is the code-review companion to the [Engineering Philosophy](PHILOSOPHY.md). Where that document names the general principles that guide how we think — fix the root cause, never hide a failure, performance and reliability are features — this one is deliberately about *minutiae*: the specific, concrete patterns in a diff that should make a reviewer stop and dig deeper. Each red flag below is a change that is very rarely legitimate and far more often a workaround dressed up as a fix, and the common thread is skepticism: **a reviewer should never accept the author's written justification at face value.** A PR description explaining *why* a timeout was raised or a heap was grown is a claim, not evidence; the review's job is to demand the mechanism — the specific, verifiable cause — and to reject the change if the mechanism offered is a symptom ("it was slow", "the host was busy") rather than a cause.

## This List Is Not Exhaustive

The red flags below are the most common and most damaging offenders, the ones that have cost real outages and real debugging time. They are not a complete catalogue of code smells, and the absence of a pattern from this document is never a reason to wave it through. A reviewer who notices something that looks wrong — duplicated logic, a function doing two unrelated jobs, a name that does not match what the code does, a boolean parameter that switches behavior, a comment apologizing for the code under it, a dependency pointing the wrong way, anything that makes the change harder to reason about than the problem warrants — should investigate it with the same seriousness as the named cases: find out why the code has that shape, and whether a cleaner one exists. "It isn't on the list" is not a defense an author may offer, and not a reason a reviewer may accept.

## Written Justifications Deserve Extra Scrutiny

An explanation attached to a questionable choice — a long code comment defending a workaround, a PR description arguing that a special case is safe, a commit message explaining why the usual rule does not apply here — is itself a signal to look harder, not a reason to relax. This matters most for changes written by AI models, and weaker models in particular: when such a model produces code that takes a shortcut, it will often also produce a fluent, confident, plausible-sounding argument for why the shortcut is correct. The argument is generated to fit the code, not the other way round, so its persuasiveness says nothing about whether it is true. A careful paragraph of reasoning beside a timeout increase, an exemption, a weakened assertion, or a swallowed error should therefore attract *more* scrutiny than the same change with no explanation at all. No such claim is accepted at face value. The reviewer verifies it independently: check each stated fact against the code and the evidence, look for the root cause the justification is standing in for, and work out for themselves whether a better approach exists rather than trusting the author's statement that none does. Cases where an exception to these rules is genuinely justified are extremely rare. One is established only when the reviewer has confirmed, by their own investigation, that there really is no better approach — never because the author said so, however well.

## Reflection

Use of reflection is strongly discouraged, in main source code and in tests alike. Reflection trades away static type checking, defeats the compiler's ability to verify that a call site and its target agree, hides dependencies from anyone reading or refactoring the code, and breaks under the [SJVM sandbox](architecture/STANDARD_LAYERED_ARCHITECTURE.md#sandboxed-execution-and-security), where sandboxed code has no reflection access at all. When code genuinely needs to work with types or members that are not known until build time, the strongly preferred alternative is *code generation* — invoking the Kotlin compiler to compile generated source, or generating bytecode directly with ASM — so that the result is ordinary, statically-checked code rather than stringly-typed lookups resolved at runtime. In tests, reaching for reflection to poke at private internals is a second red flag layered on the first: tests should only ever exercise a module's public API (see [Test the Public API Only](architecture/TESTING.md#test-the-public-api-only) and [Tests Must Only Exercise the Public API](#tests-must-only-exercise-the-public-api)). A diff that introduces `java.lang.reflect`, `kotlin.reflect`, `setAccessible`, or a `Class.forName` lookup should be challenged to justify why generated code cannot do the job.

## Regular Expressions

A regular expression in a diff is a red flag, and there is almost always a better tool for the job. A regex is reached for far more often than it is warranted — usually to out-clever a problem that a plain string predicate (`contains`, `startsWith`, `split`, a small `when`) would express more clearly, and usually to guard an edge case that does not actually occur. A regex is dense by design: a single expression compresses an entire matching policy into punctuation, so the set of inputs it *silently declines to match* is invisible at the call site. That invisibility is the real hazard, because a matcher that quietly fails to match can fail in the dangerous direction — letting through, or rejecting, an input the author never pictured — with no loud error to announce it. [build-watchman #8](https://github.com/CodexCoder21Organization/build-watchman/pull/8) is the cautionary case: to recognize GitHub's "already in the merge queue" enqueue rejection, an early revision added a regex requiring a queue word within a fixed `{0,4}`-word window of "already", specifically to rule out a contrived false match nobody could actually produce. The window was a magic number that would silently *stop matching* the instant GitHub reworded the message one word longer — and a miss there did not throw or warn, it re-armed the exact startup-exit bug the matcher existed to prevent. The fix deleted the regex in favor of a handful of commented `contains(...)` checks a reader can audit at a glance, which fail toward *matching* (the safe direction there, since a false match self-corrects on the next poll while a missed match reintroduces the bug). When a reviewer sees a `Regex(...)`, the question is not "is this pattern correct?" but "what is the simplest string check that makes the accepted and rejected inputs obvious to the next reader, and does it fail toward the safe outcome when it meets something new?" Do not reach for a regex — or any cleverness — to defend against an edge case you cannot demonstrate (see [Avoid Special Cases, Optimize the General Case](PHILOSOPHY.md#avoid-special-cases-optimize-the-general-case)).

The reflexive defense — "but the input is *structured*" — does not rescue the regex; it disqualifies it. When the input has a real format (a date, a URL, a semantic version, JSON, a CLI argument string, the source of a language), the correct tool is the library built to parse that format — `org.json` for JSON, a URL/URI type for URLs, a date-time library for timestamps, a semantic-version parser for versions, `commons-cli` for arguments, a real grammar or parser for a language — never a regex approximating it. A regex that reimplements a parser *is* a hand-rolled parser, with the format's hard cases (escaping, encodings, optional fields, Unicode, nesting, comments) silently missing and untested against the format's real corpus: the same rewrite-from-scratch mistake the ecosystem's library conventions exist to prevent, only denser and harder to read. So when a regex tempts you there are two honest responses, and neither is a regex: for loose keyword or prose matching, a couple of `contains`/`startsWith` calls; for structured input, the parsing library for that format.

## Timeout Increases

Any increase to a timeout is a huge red flag. It is almost always a workaround rather than a fix: the code got slower, or hangs intermittently, and instead of finding out *why*, the author moved the threshold that was catching it. Examine every such change with skepticism and do not blindly trust the written justification — a timeout that "needs" to be increased is a bug that has not yet been understood (see [Fix the Root Cause, Never Mask the Symptom](PHILOSOPHY.md#fix-the-root-cause-never-mask-the-symptom) and [Symptoms vs. Causes, Generally](architecture/TESTING.md#symptoms-vs-causes-generally)).

There is a narrow class of legitimate increase, and it is distinguishable because it can be *quantified*. An overall build timeout may genuinely need to grow if a suite has accumulated many new tests over time while the ceiling stayed fixed — but even then, the increase must be justified by examining the tests that were added and how long they actually take to run, and the new ceiling must be no larger than that measured growth supports. "The build is timing out, so I doubled it" does not meet that bar; "we added 214 tests since the ceiling was set, they run in 6m40s, so the 20m ceiling becomes 27m" does. If the author cannot produce the accounting, the timeout stays and the investigation continues. Blindly increasing timeouts makes everything worse: it hides real underlying problems, erodes the thresholds that exist to catch regressions before users do, and makes every future slowdown harder to notice.

## Hardware-Dependent Test Bounds

Any test bound that depends on which machine runs the test — and any plan that involves finding out — is a huge red flag. The tell is often a sentence rather than a diff: "the bound needs to be investigated on the build hardware," "this passes locally but the CI host is slower," a timeout conditional on the environment, or a threshold chosen by benchmarking a particular box. Each of these encodes a machine's speed into a test's contract, producing a test that flakes on the next hardware change while verifying nothing about the code. A well-designed test never requires knowing what hardware it runs on: its timeout is generous enough that a healthy run passes on any plausible host, and a bound guarding against super-linear growth is separated by orders of magnitude — N chosen so the defective O(N²) cost is incomprehensibly large on any machine while the fixed cost stays comfortably inside the timeout — or replaced outright by a hardware-independent work count from an in-memory dependency. A reviewer who sees a per-environment threshold, a CI-specific multiplier, or an author proposing to characterize a test's performance on the build machine should send the change back to be restructured around [asymptotic separation or work counting](architecture/TESTING.md#test-verdicts-must-be-hardware-independent); this is the same move as a [timeout increase](#timeout-increases) — tuning the referee instead of fixing the game. The same flag applies to reproducers, not just bounds: a reproducer must never be calibrated to a machine, so a flake reproducer whose concurrency was tuned until the failure appeared on one particular host must be sent back to be restructured around a [deterministic trigger of the condition the code must tolerate](architecture/TESTING.md#never-calibrate-a-reproducer-to-a-machine).

## Resource Increases

Any increase in resource allocation — a bigger JVM heap (`-Xmx`), a larger container memory limit, more CPUs, a bigger droplet — is a huge red flag, and is usually a workaround rather than a fix for the underlying root cause. Examine such changes with the same skepticism as timeout increases and do not blindly trust the author's justification. There is almost never a legitimate reason to grow a heap or request bigger hardware: computers are fast, the workloads in this ecosystem are small, and a memory or CPU increase almost always means there is a memory leak or that memory is being used inefficiently — most commonly a large payload being materialized in heap instead of streamed (see [When It Is Not a Leak: Materializing Instead of Streaming](architecture/TESTING.md#when-it-is-not-a-leak-materializing-instead-of-streaming)). The correct response to an `OutOfMemoryError` is a heap dump and a diagnosis of what is actually retained, never a larger `-Xmx` — [Resolving OutOfMemoryErrors](playbooks/OOM.md) is the single entry point for that investigation (see also [OOMs Are Symptoms of Memory Leaks, Not Bugs to Be Handled](architecture/TESTING.md#ooms-are-symptoms-of-memory-leaks-not-bugs-to-be-handled), and the [topic resources](#topic-specific-reviewer-resources) entry for any PR that mentions an OOM at all). Fix the underlying problem; do not raise memory or CPU limits, and do not request more or bigger hardware. The mirror image is a red flag too: a diff that deploys a service, launches a process, or forks a JVM with *no* cap on memory, CPU, or disk — or that removes one — leaves a single leak free to starve every neighbour on the machine, against [Contain the Blast Radius](PHILOSOPHY.md#contain-the-blast-radius-a-bug-in-one-module-never-starves-another); every unit gets an explicit, enforced cap sized from measured healthy usage, per [Isolation](architecture/ISOLATION.md).

## Memory That Grows with Service History

Any in-memory structure whose size scales with the service's accumulated usage is a huge red flag, even when the diff runs perfectly today: loading an entire event log into memory to process it, an in-memory projection or map that gains an entry for every event, record, or run the service has ever seen, a startup path that parses a whole history file, a cache keyed by an unbounded id space with no eviction. Such code passes every test and every demo — the datasets there are small — and then takes the service down weeks into production when history exceeds the heap, at which point it invites the two follow-on mistakes this document already flags: a [resource increase](#resource-increases) or a [bounded read that drops data](#bounded-reads-that-drop-data). The rule to review against is that **heap must be proportional to the working set of the current request, never to the size of accumulated history**: event logs and other growing datasets are processed as streams (cursor iteration, incremental writes), and projections that grow with usage are randomly accessible from persistent storage — a file-backed hash map such as MapDB, a SQLite database, or a real database service — never mirrored in heap (see [CQRS — Materializing Projections](architecture/CQRS.md#materializing-projections), [Embedded — Sizing Memory for Growing Datasets](architecture/EMBEDDED.md#sizing-memory-for-growing-datasets), and [Testing — When It Is Not a Leak: Materializing Instead of Streaming](architecture/TESTING.md#when-it-is-not-a-leak-materializing-instead-of-streaming)). A reviewer who sees a `readAll()`-shaped call on a growing source, a collection that only ever gains entries, or a whole-history load at startup should ask one question: *what is this structure's heap footprint after two years of production usage?* If the answer is proportional to usage, the change goes back for a streaming or persistent-storage shape. A subtler species of the same flag is the in-memory cache of an *expensive* derived value — a computation taking seconds or minutes whose result is held only in heap, so every eviction and every restart silently re-pays the full cost. That one is a judgement call rather than an absolute — weigh the projection's size, how quickly it goes stale, whether it can be updated incrementally or must be recomputed wholesale anyway, and the required response times — but the balance in practice drifts too far toward in-memory, so the reviewer's question is: *why is this not a disk-persisted projection updated incrementally?* (see [CQRS — Persist Expensive Projections](architecture/CQRS.md#persist-expensive-projections)).

An incremental design does not by itself make a change safe, and the reviewer's job is to find the **full-scan path sitting beside it**. The most convincing version of this red flag arrives in a diff that already *looks* correct — a syncer with a watermark, a cursor, and a page size, pulling new records a few hundred at a time — because a reviewer who confirms the fetch is paged tends to stop there. The defect hides in the paths that are not the fetch: an id set built by enumerating every record in the store to work out what has already been indexed (`listDocuments(bucket).map { it.id }.toHashSet()`), a count obtained by listing a whole collection and taking its `.size`, a startup validation that reads the entire corpus "to force it to be readable", or a rebuild that discards the watermark (`sinceMillis = 0L`, `cursor = null`) and re-pulls the whole of history whenever a schema generation changes or a single record turns up missing. Each of those is O(total history) inside a design whose steady state is O(new records), and each is invisible in testing because a fresh store and a full re-sync cost the same when the corpus is small. The questions to ask are therefore narrower than "is this incremental?": **which calls in this diff touch every record rather than only the new ones, and what happens to the watermark on a rebuild?** An enumeration used only to compute set membership or a count belongs in the store as an indexed lookup or a maintained counter, and a rebuild must resume from a durable position rather than restarting from zero (see [CQRS — Materializing Projections](architecture/CQRS.md#materializing-projections) and [Api — Streaming and Pagination](architecture/API.md#streaming-and-pagination)). Both halves must hold for the change to be safe: streaming the transfer while still enumerating the corpus on every pass simply moves the unbounded cost from the network to the heap.

## Bounded Reads That Drop Data

A diff that responds to memory growth by bounding a read — "only read the last 1,000 records from the event log," a `.takeLast(n)` over a growing dataset, a `LIMIT` with no cursor to fetch the rest — is a huge red flag, and the word "bounded" in a PR description is itself the trigger to look closely, because it is the word authors reach for when the honest word is *truncated*. Bounding a cache or a chunk is legitimate engineering; "bounding" a dataset read is data loss wearing bounding's clothes: a projection built from a suffix of the log is wrong by construction, since any record outside the window is silently never processed and a valid data item simply fails to appear where it should have — no error, no warning, just a quietly incomplete answer. And because the function's signature stays put while its answers change, this is simultaneously a [silent contract change](#silent-contract-changes-to-an-existing-api) for every existing consumer. The discriminator the reviewer should apply: *could discarding this data change the answer of any query?* A fixed-size cache in front of authoritative storage cannot (a miss just reloads); a streaming chunk size cannot (every chunk is still processed); a page size with a cursor cannot (the caller fetches the rest). A last-N read of an event log can — so it is truncation, and the memory problem it was papering over still needs its real fix: streaming/chunking and persistent projections per [Memory That Grows with Service History](#memory-that-grows-with-service-history). Indexing or a purpose-built projection is a fine complement — a way to jump directly to the relevant records instead of scanning everything — provided the index does not itself grow heap unboundedly and indexed result sets are bounded by the query's semantics (a `WHERE` clause, pagination), never by discarding matches (see [CQRS — Anti-Pattern: Bounding Reads by Dropping Data](architecture/CQRS.md#anti-pattern-bounding-reads-by-dropping-data) and [Api — Streaming and Pagination](architecture/API.md#streaming-and-pagination)).

## Claims That a Host Is Overloaded

Any claim that a host is overloaded, over capacity, or otherwise saturated — offered as the explanation for a failure, or as justification for adding hardware, moving a service, reducing parallelization, relaxing a limit, etc — is a huge red flag and deserves the same skepticism as a resource increase, because it is the same move in different clothes. An apparently overloaded box is a *symptom*: of a memory leak, a thread leak, a runaway respawn loop, non-linear gossip, or a JVM allocating heap until the OS swaps — not a fact of nature to be accommodated with a bigger machine (see [The Host Is Almost Never Over Capacity](architecture/TESTING.md#the-host-is-almost-never-over-capacity) and [Performance and Reliability Are Features](PHILOSOPHY.md#performance-and-reliability-are-features)). A reviewer confronted with "the host was saturated" should ask what forensic evidence — heap dumps, thread dumps, process lists, connection state — identifies the process and mechanism doing the saturating. If the answer is load averages and free-memory numbers alone, those are consequences, not causes, and the underlying defect is still at large.

## Unmeasured Performance Claims

Any change justified in the name of performance — "this avoids a copy", "this removes an allocation", "this is faster under load" — that is not backed by a concrete runtime profile is a huge red flag. Performance intuition drawn from *reading* the code is wrong far more often than it is right: the bottleneck a diff claims to fix is frequently not where the author thinks it is, and a change that looks faster on the page can be neutral or worse in production while adding complexity that must be maintained forever. The review's job is to distinguish a measured optimization from a plausible story, and the discriminator is evidence taken from the running system — a heap dump, a `jstack` sample, a `jstat -gcutil` reading, a `vmstat`/`top` capture — not the elegance of the argument. A reviewer confronted with a performance claim should ask two questions and accept nothing less: *what production profile or trace demonstrates this bottleneck, and what measurement shows the fix actually helps?* An optimization supported only by code examination, with no runtime trace behind it, has not been shown to help at all and may be pure risk; treat it with the same skepticism as a [resource increase](#resource-increases) or a [claim that the host is overloaded](#claims-that-a-host-is-overloaded) — both of which are the same move in different clothes — and challenge it to produce the measurement before it lands. A particular sub-species deserves naming: a change that *caps* rather than *fixes* — an admission-control gate, a bounded-concurrency semaphore, a queue-depth limit, or any throttle added to "keep the system below its saturation point" — is doubly disqualified, because it is both unmeasured and a workaround that masks the defect instead of removing it. It is most egregious when bolted onto a lightweight coordinator or manager service that merely delegates its real work to workers on other hardware: such a manager should never saturate, so a concurrency cap there hides a manager that is doing too much per operation rather than fixing it — the underlying cost must be profiled and removed systemically (see [Measure Performance, Never Speculate About It](PHILOSOPHY.md#measure-performance-never-speculate-about-it) and [Prefer Cattle Over Pets](PHILOSOPHY.md#prefer-cattle-over-pets-isolated-services-that-outlive-their-manager)). Performance fixes are guided by traces taken from production and repaired at their source, never by staring at the code and never by throttling around the symptom.

## A Dearth of Test Coverage

Any PR with a dearth of test coverage is a huge red flag. The reasoning is simple: any change worth making is worth testing, and if the change fixes a bug that existed in the previous version, then by definition the existing test coverage was inadequate to discover that bug — so the change must itself add the comprehensive coverage that was missing, not merely alter the implementation and lean on the tests that already failed to catch the problem. The coverage that counts is comprehensive end-to-end integration testing: tests that exercise the public API against real instances of dependencies and verify the observable behavior the change claims to deliver, including the edge cases and failure modes around it (see [Test End-to-End Against Real Dependencies](PHILOSOPHY.md#test-end-to-end-against-real-dependencies) and [End-to-End Tests, Not Mocks](architecture/TESTING.md#end-to-end-tests-not-mocks)). For a bug fix specifically, the review should confirm the PR contains a test that reproduces the bug and failed before the fix — a fix without a reproducing test is a guess (see [Reproduce a Bug Before You Fix It](PHILOSOPHY.md#reproduce-a-bug-before-you-fix-it) and the [Bug Fix Testing Workflow](architecture/TESTING.md#bug-fix-testing-workflow)). A diff that changes behavior while leaving the test suite untouched, or that gestures at "covered by existing tests," should be challenged to name the test that verifies the new behavior — and if none exists, to write it. The same reasoning applies to a bug the review itself finds that affects publicly visible behavior: the suite was green with that bug present, so the finding goes back to be fixed test-first — a test that fails for the reason the finding names, then the fix, then that test green — followed by a search for the other gaps in the coverage around the change, per [Testing — Ultrathink: Are the Tests Comprehensive?](architecture/TESTING.md#ultrathink-are-the-tests-comprehensive). A finding with no publicly visible effect, such as the use of [Reflection](#reflection) or a questionable design decision, is fixed all the same, without a test. The mirror image of this flag — a PR that modifies the tests it already had rather than failing to add new ones — is [Weakening an Existing Test](#weakening-an-existing-test).

Coverage is not comprehensive until it reaches the **extreme conditions**, and this is the point at which the growth- and scale-shaped red flags above most often escape review. Any change whose heap, latency, or work scales with something — accumulated history, corpus size, concurrent callers, payload size — must arrive with a test that drives that dimension to production scale and past it, per [Extreme-Condition Testing](architecture/TESTING.md#extreme-condition-testing-load-fuzzing-failure-injection-and-chaos). The most valuable form is the one the ecosystem's defaults already make cheap: a [load and soak test run under the smallest realistic heap](architecture/TESTING.md#load-saturation-and-soak) — the forked JVM's 128 MB default, never raised — sustained over enough iterations that an unbounded structure, a full-corpus scan, or a per-request retention surfaces as an `OutOfMemoryError` inside CI rather than weeks later in production, with the memory, descriptor, and thread curves asserted flat at the end. Oversized and adversarial inputs belong in the same pass ([Adversarial and Oversized Inputs](architecture/TESTING.md#adversarial-and-oversized-inputs-fuzzing)), as does a dependency that dies mid-call and a service restarted onto its own persistent state ([Failure Injection and Crash Recovery](architecture/TESTING.md#failure-injection-and-crash-recovery)). A reviewer should treat "it works, and the unit tests pass" as saying nothing whatsoever about scale, because a growth-shaped defect passes every small-dataset test by construction — the datasets in the suite and the demo are tiny, so the full scan and the incremental path cost the same there. The question to put to the author is therefore *which test fails if this structure grows unbounded, and at what size did you actually run it?* If no such test exists, that absence is itself the review finding, and the change goes back with the extreme-condition test attached rather than with a reassurance that today's data is small.

## Unbounded Inputs and Variable-Size Data Without a Scale Test

Extreme conditions never appear in a diff — they happen in production, months later. What *does* appear in a diff, and is the red flag, is **any Api or implementation behavior whose inputs are unbounded or whose data size is variable**: a parameter, collection, payload, history, cache, queue, or caller count whose size is decided by the world rather than fixed by the contract. Every such thing in the diff, and in the path the diff touches, is a place where production's worst case lives, and the reviewer's question for each is: *what bounds this, and which test drives it past production scale?* — asked of the **touched path**, not only of the lines that changed. The two red flags above are special cases of this one; this one is the general obligation, and it is the one that most often fails to trigger, because a diff that merely edits a path with variable-size data "introduces no scaling" and a diff-shaped review finds nothing to object to. That is how, in October 2026, the BuildTest projections went stale for most of a day: a replay that recomputed per-run counts from every row of the run on every event (work per row proportional to run size), and a per-run cache that materialized every completed run's results with release paths but no bound (heap proportional to history) — both correct at test scale, neither tested at production scale, both last touched by diffs that changed something else.

For each unbounded or variable-size thing in the touched path, the review names the test that reaches production scale and past it, per [Extreme-Condition Testing](architecture/TESTING.md#extreme-condition-testing-load-fuzzing-failure-injection-and-chaos), with a verdict that is [independent of hardware](architecture/TESTING.md#test-verdicts-must-be-hardware-independent): a **work count** or asymptotic separation for the cost curve ([linear, not catastrophic](architecture/TESTING.md#load-saturation-and-soak)); a **flat heap, descriptor and thread curve** for a soak; and a **shrunk configured limit** for anything the design retains on purpose, so that growth with history fails in a test of a few iterations rather than weeks into production ([Bound What the Design Retains on Purpose](architecture/TESTING.md#load-saturation-and-soak)). If no such test exists, that is the finding; "the diff did not change that" is not a defence, and the remedy is the missing test — followed by whatever defect it exposes — never a sentence in the description. A review brief that does not ask for this enumeration, and a review that does not state per touched path what is unbounded and which test covers it, are both incomplete.

**Where it hides.** These are the places this red flag has actually bitten in this ecosystem, the obvious ones first and the ones that have surprised reviewers after:

- **Restoring a projection at startup** — replaying the whole journal, re-hashing every stored record, or restoring every advertised snapshot before the service reports ready, so startup time grows with history until it crosses the host's readiness deadline and the service death-loops. The bound is a persisted checkpoint and lazy restoration of anything not needed for readiness.
- **Per-event recomputation during a replay** — recounting or re-aggregating a whole run, bucket or page for every row applied, so replay work is rows × rows-per-run instead of rows. The bound is one aggregation per affected unit per page.
- **A cache of completed work with release paths but no bound** — per-run, per-record or per-event state kept "by design" and released only on explicit invalidation, so heap tracks history. The bound is an explicit byte or entry limit asserted against a shrunk configured value.
- **The full-scan path beside the paged one** — an id set built by enumerating every record, a count taken as `.size` of a whole listing, a startup validation that reads the corpus "to make sure it is readable", a rebuild that resets the cursor to zero ([Memory That Grows with Service History](#memory-that-grows-with-service-history)).
- **A per-query scan of the corpus** — a search or filter that walks every stored item per request; correct and fast at a thousand items, a 30-second handler at a million.
- **Materializing before encoding** — a bounded page that is still assembled, serialized and buffered whole before it is sent, so the encoded response, the outbound buffer or a relay's reassembly becomes the unbounded thing even though the page size was capped. The bound is a response-size budget enforced where the bytes are produced, and streaming past it.
- **Parse amplification** — an input of N bytes whose decoded form costs many times N in heap (a request body parsed into a tree, a compressed payload expanded, a snapshot decoded into objects). Charge the worst-case decoded footprint, not the wire size.
- **Retry amplification by consumers** — several readers each re-requesting a large page every few seconds when a slow handler times out, multiplying the load that made it slow. Timeouts and retries are not bounds; a typed refusal and backpressure are.
- **Unbounded outbound buffers on dead or slow connections** — writes queued to a peer that never drains them until the writer's heap is gone.
- **Loading a growing file to append to it** — a history, index or manifest read whole and rewritten on every update.
- **Startup hashing or validation of every stored artifact** — a digest of the whole store "to detect corruption", linear in history and run before readiness.
- **Test-time multipliers** — a test that compiles or hashes inside the test JVM under the runner's parallelism, where a toolchain change to the child JVM's compilation policy moves the cost across a fixed limit; the data size here is the compile input and the classpath (hundreds of inherited archives), both variable and both inherited silently.

## Weakening an Existing Test

Any change to an existing test is a red flag until the reviewer has established that the test's constraints are at least as strong after the diff as before. [A dearth of test coverage](#a-dearth-of-test-coverage) is the flag for the tests a PR should have added; this is the flag for the tests it already had, and it is the more dangerous of the two, because a weakened test does not merely leave a gap — it leaves a *green* one, still named after the behavior it no longer verifies and still counted as coverage by everyone who reads the suite. The rule to review against is that **an existing test's constraints may be strengthened freely and relaxed only deliberately**, so every hunk touching a test file earns a line-by-line read of what the *old* code required, not merely a check that the new code looks reasonable.

The overt forms are the ones a reviewer already knows to catch: a deleted assertion, `assertEquals` softened to `assertNotNull`, an expected value broadened until nearly anything matches, a `try`/`catch` wrapped around a test body, an `@Disabled` or `assumeTrue` guard, a raised timeout or poll budget. Each of those is prohibited outright rather than merely suspicious (see [Never Hide a Failure](PHILOSOPHY.md#never-hide-a-failure), [Never Skip Tests](architecture/TESTING.md#never-skip-tests), and [Timeout Increases](#timeout-increases)).

The subtle forms are the reason this section exists, because they weaken a test without touching an assertion at all — they change the *conditions the assertions run under*, so every assertion in the file still reads as strict while the scenario that used to break it simply no longer occurs. Watch for:

- **Concurrency removed or reduced.** A parallel `async { … }.awaitAll()` rewritten as a serial `repeat`, a thread or coroutine count dropped, a newly introduced semaphore capping parallelism to one, a shared instance quietly given a fresh copy per iteration. A test whose entire purpose was to put two callers inside the same code path at the same moment verifies nothing once they take turns — the interleaving *is* the test, and removing it deletes the only mechanism that was exercising the race (see [Prefer Parallel Iterations Over Serial `repeat`](architecture/TESTING.md#prefer-parallel-iterations-over-serial-repeat)).
- **Synchronization added to the test itself.** A latch, a barrier, a `sleep`, or an `await` inserted *between* the operations whose overlap was the point, or ordering imposed on requests that were deliberately racing. This is the same deletion of the race as above, wearing the costume of a fix.
- **Iteration counts, payload sizes, and datasets shrunk.** Fewer iterations, a smaller body, fewer records, a shorter soak. These are the amplifiers that make a rare interleaving observable and let a leak accumulate to the point of visibility; reducing them is forbidden in its own right, and reducing them *because the test was flaky* is the classic move.
- **Inputs narrowed.** Randomized or generated input pinned to a fixed seed or a single hand-picked value, an edge case dropped from a parameterized list, a boundary value nudged inward, an adversarial input replaced with a well-formed one.
- **A real dependency swapped for a fake.** Replacing a genuinely started instance with an in-memory stand-in shortens the path the test covers, and everything between the two disappears from coverage silently (see [End-to-End Tests, Not Mocks](architecture/TESTING.md#end-to-end-tests-not-mocks)). Adding an in-memory implementation to *inject a fault the real dependency cannot be made to produce* is the legitimate case and strengthens the suite; substituting one for a real dependency the test was already exercising end-to-end is this flag (see [In-Memory Implementations for Error Simulation](architecture/TESTING.md#in-memory-implementations-for-error-simulation)).
- **The observable outcome replaced by a proxy for it.** Asserting that a log line appeared, a flag flipped, or a method was reached, instead of asserting that the client actually received the right answer. By construction more cases now pass — including the ones where the work starts and then hangs partway (the [ContainerNursery case study](architecture/TESTING.md#case-study-root-cause-vs-symptom-treatment) is precisely this mistake, caught in review).
- **Order, completeness, or exactness quietly dropped.** An ordered comparison relaxed to set equality, an exact collection match relaxed to `contains`, one expected outcome relaxed to "either of these is acceptable", or a newly added `finally` that closes the very resource whose accumulation the test existed to detect.

**The reviewer's question for every modified test is: run against the code as it stood *before* this PR, would this test still fail?** Where the test was written to catch a specific defect, that question has a checkable answer — ask the author to revert the production change, run the modified test, and show it going red. A modified test that no longer fails against the old code has been weakened no matter how the diff reads, and the burden is on the author to justify the relaxation, not on the reviewer to prove it happened.

Flaky tests are where this pressure concentrates, and **a flake is a defect in the code under test until proven otherwise, so that is where the fix belongs**. [Every flake is a real defect](architecture/TESTING.md#every-flake-is-a-real-defect--trace-it-through-dependencies-and-infrastructure): the race, the leak, the unbounded wait, the ordering assumption is genuinely there, and that it surfaces intermittently in CI rather than deterministically in production is luck rather than a difference in kind. A PR that answers a flaky test by editing the test is therefore making a specific claim — that the code under test is *verifiably correct* and the test itself is the true problem — and "verifiably" is the word the review must hold it to. That claim is discharged by naming the mechanism that shows the existing test asserts something the contract never promised (a dependence on `HashMap` iteration order, wall-clock timing where a [`Clock`](architecture/TESTING.md#clock-abstraction) belongs, a port collision, state leaking in from another test), never by "the code looks correct", "it passes locally", or a green re-run. Absent that mechanism the test edit is [symptom mitigation](PHILOSOPHY.md#fix-the-root-cause-never-mask-the-symptom), and it costs more than it appears to: it destroys the one reproducer of a defect that is still live in production, and it teaches the next investigator that this test's failures are noise. Where a test genuinely is wrong, the correction is made explicitly and on its own terms — rewritten to assert the real contract, not trimmed until it stops failing — and it still owes the reliable reproducer the [Flaky Test Policy](architecture/TESTING.md#flaky-test-policy) requires.

Finally, a test modification riding along inside a PR about something else is its own flag. Relaxations arrive most often as a "small fix to unblock CI" tucked into a diff whose stated subject is a feature, exactly where a reviewer's attention is elsewhere. Any test edit whose motivation is not stated in the PR description should be asked about directly, and one whose motivation turns out to be "the build was red" should be treated as a flake investigation that has not happened yet.

## Tests Must Only Exercise the Public API

A test is a red flag whenever it observes or manipulates anything a real caller of the component could not. The standard every test is held to is [Test the Public API Only](architecture/TESTING.md#test-the-public-api-only): a test exercises the surface end users invoke, and asserts only on what is observable through the public contract — results, errors, effects, callbacks, state visible through other public operations, and work crossing a dependency's Api boundary. The check the reviewer applies is a thought experiment: **if the implementation were thrown away and rewritten from scratch, honouring every public contract but sharing no code, no file layout, and no data structure with the old one, would this test still compile and still pass?** A test that would break is coupled to the implementation rather than to the contract, and it is worth less than it appears in two directions at once: it fails on harmless refactorings, teaching everyone that its failures are noise, and it keeps passing through a genuine regression that happens to leave the internals looking the same.

That rewrite question is the test; the shapes below are only the ways it most often fails in practice, and a test can fail it in a form not listed here (see [This List Is Not Exhaustive](#this-list-is-not-exhaustive)):

- **Reading or writing the service's private state directly.** Pre-seeding a journal, database, or cache directory so the service "already has" records; asserting on the files, tables, or bytes it stores for itself; inspecting a map, queue, or counter it keeps for its own use. This is the same ownership violation as [Reaching Into Another Component's Private Files or Internal Layout](#reaching-into-another-components-private-files-or-internal-layout), applied by a component's own tests to its own internals, and it covers in-memory structure as much as persisted state. State is seeded through the public operations that create it and verified through the public operations that observe it. (A crash-recovery test that restarts a service against the *same* persistent directory, treating its contents as opaque, is not this flag — it never reads or writes those files itself.)
- **Asserting on internal mechanism rather than observable outcome.** That an internal cache was hit rather than missed, that a particular private helper ran, that a lock was taken, that an internal executor's queue drained. None of these is a promise the component makes to its callers. Where the mechanism has a consequence a caller can observe — a result is still served after the dependency failed, a count of calls arrives at a dependency's Api boundary (work crossing a dependency boundary *is* contract behavior; see [In-Memory Implementations for Error Simulation](architecture/TESTING.md#in-memory-implementations-for-error-simulation)) — the test asserts that consequence instead; where it has none, it is an implementation detail the test has no business depending on. The same substitution running the other way, an observable outcome replaced by a proxy such as a log line, is listed under [Weakening an Existing Test](#weakening-an-existing-test).
- **Visibility widened, or surface added, to let the test in.** A `private` turned `internal`, an `internal` turned `public`, a getter or hook that exposes the component's private state for assertion, a method added to the Api whose only purpose is to let a test read what callers were never meant to see. Each freezes the shape of an internal and adds surface real callers should not use. This is distinct from completing a genuinely incomplete contract — the offscreen rendering entry point that [GUI screenshot tests](architecture/TESTING.md#gui-screenshot-tests-mandatory) require is a real public operation, not a window onto internals — and distinct from dependency injection: a [`Clock`](architecture/TESTING.md#clock-abstraction) parameter defaulting to `SystemClock`, a filesystem, or an in-memory implementation of a real dependency Api, each of which the production code path consumes too, is legitimate even when tests are the only callers that pass it explicitly. The answer to "I cannot reach this through the API" is to test through the existing API, to complete the contract, or to [extract the logic into its own submodule](architecture/TESTING.md#extract-submodules-instead-of-increasing-visibility) with a public API of its own — never to expose the internal.
- **Test-only entry points in production code.** A `testMode` flag, a `forTesting` constructor, an [environment variable](architecture/TESTING.md#no-environment-variables-in-tests) that switches off a code path, a seam whose only purpose is to let a test bypass a step. Beyond coupling the test to internals, such an entry point ships to production, where it is an untested path at best and a bypass at worst. The injection seams named above are the legitimate alternative: a dependency the real implementation consumes, never a switch inside the component. Reaching in by [reflection](#reflection), `setAccessible`, or direct instantiation of internal classes is the same flag without even the pretence of an entry point.
- **Dependence on incidental behavior the contract does not promise.** Iteration order of an unordered collection, identifiers that happen to be sequential, the number of internal operations behind one public call, timing that happens to hold on today's implementation. These pass today and fail on the first legitimate change, and the failure then looks like a flake. (Error and warning text is part of the public contract and is asserted in full per [Error and Warning Assertions](architecture/TESTING.md#error-and-warning-assertions); this bullet is about incidental diagnostics, not contractual messages.)

The reviewer's questions for any test that touches something a caller could not: *what behavior visible through the public API does this internal state or mechanism produce, and why is the test not asserting that? If nothing visible depends on it, why does the test care?* When the honest answer is that the behavior genuinely cannot be reached through the public API, that is a finding against the API or the component's boundaries, not a licence for the test — the design is reconsidered, per [Test the Public API Only](architecture/TESTING.md#test-the-public-api-only), rather than the encapsulation weakened. "It is the only way to test this" is a claim to be examined, not a justification to accept; the rewrite question above is what decides it.

## Tests Must Be Hermetically Sealed

A test whose result can change because of something the test did not itself create and control is a red flag, however green it is today. The standard is [Tests Must Be Hermetically Sealed](architecture/TESTING.md#tests-must-be-hermetically-sealed), and its deciding question is the one the reviewer asks of every added or changed test: **could this test pass on one machine and fail on another, or pass when run alone and fail inside the full suite?** If the answer is yes, the test has an input it depends on but does not own, and that input is a defect to close before the test is merged — not a quirk to tolerate, and not something to find out about later as a flake.

The unsealed inputs that come up most often, each with the section of the testing document that governs it (the list is not complete, per [This List Is Not Exhaustive](#this-list-is-not-exhaustive)): a shared or production endpoint reached instead of an isolated node the test starts itself ([No Production Services in Tests](architecture/TESTING.md#no-production-services-in-tests)); a pre-existing or shared on-disk path or database where an in-memory one belongs, a fixed port number, or a resource opened and never released ([Side-Effect Isolation](architecture/TESTING.md#side-effect-isolation) — a directory the test itself creates and a crash-recovery test restarts against, or a committed golden screenshot, is test-owned and not this flag); configuration read from an environment variable or other process-global state rather than passed as a parameter ([No Environment Variables in Tests](architecture/TESTING.md#no-environment-variables-in-tests)); a wall-clock wait or `sleep` where a `ManualClock` belongs ([Clock Abstraction](architecture/TESTING.md#clock-abstraction)); and a fixture, helper source, or mutable object shared with a sibling test inside the test tree ([Every Test Must Be Fully Isolated](architecture/TESTING.md#every-test-must-be-fully-isolated) — a versioned utility imported as a Maven artifact is not). The same flag covers the leaks no list names — the host's locale, timezone, or DNS resolver, a background thread left running into the next test, hash-map iteration order — because each is the same defect: the world reaching into a test that should have sealed it out.

A reviewer who finds one does not accept "it has always passed" — a sealed test fails only for a real defect, and an unsealed one is a flake that has not happened yet, which is exactly the shape the [Flaky Test Policy](architecture/TESTING.md#flaky-test-policy) later has to diagnose at far greater cost. The reviewer asks for the mechanism first, because the unsealed input is sometimes a real race or leak in the code under test showing through: an uncontrolled test input is sealed in the test, a defect in production code, a dependency, or infrastructure is fixed at the layer that owns it — never by loosening the test, and never by waiting for CI to prove the point.

## Silent Contract Changes to an Existing API

A diff that keeps an existing function's signature while meaningfully changing what the function observably does — truncating a result that used to be complete, reordering what used to be ordered, returning partial data where it used to fail, changing an error's type or timing — is a red flag whenever the function belongs to a service with real production consumers. The signature staying put makes the change look compatible to every tool and every caller, which is exactly the danger: consumers that depend on the documented behavior break silently, with no compile error to warn them. The canonical case is an unbounded log-as-string function "fixed" by truncating the log inside the original API — the memory problem is real, but truncation changes the function's contract, and the correct fix was a new streaming function added alongside the deprecated old one. A reviewer confronted with such a change should ask two questions: *could code depending on this function's documented behavior observe a difference?* — and if so, *where are the deprecate-and-add migration and the [end-to-end tests covering every server configuration](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#testing-the-migration-matrix)?* Spotting the contract change is first and foremost the author's responsibility — it should never take a reviewer to point it out — but when one slips into a diff, the review is the last line of defense (see [Graceful Migrations & Fallbacks](architecture/GRACEFUL_MIGRATION_FALLBACKS.md) and [Migrate Heavily-Used Contracts Gracefully](PHILOSOPHY.md#migrate-heavily-used-contracts-gracefully-break-unused-ones-freely)).

## Migration Steps Without a Plan, and Big-Bang Migration Diffs

Two shapes of migration diff are red flags, and they are mirror images of each other. The first is a step of a migration — a module moved out, a contract renamed, a consumer switched onto a new system — whose pull request cannot point at the written plan it is a step of. The end state and the ordered steps toward it belong in an architecture document committed to the repository (or a PlanRepository workstream linked from it); a step with no such document is a step whose direction nobody can check, so the reviewer should ask for the plan before judging the step. The second is a single diff that performs the whole migration at once — or a set of pull requests that only work once all of them land together — which cannot be reviewed as a unit, cannot be reverted except wholesale, and cannot be kept current against `main` while it waits. The expected shape is one small, independently mergeable step that leaves `main` working and tested and moves toward the documented end state; a step that also changes the behaviour of the code it moves is two steps in one diff and should be split. See [Plan Migrations to the End, Land Them One Small Step at a Time](PHILOSOPHY.md#plan-migrations-to-the-end-land-them-one-small-step-at-a-time) and the [Planning and Landing a Migration](playbooks/MIGRATIONS.md) playbook.

## Fallbacks Inside an Implementation, and Silent Fallbacks

A fallback in a diff is a red flag until the reviewer has established which of two very different things it is. A **service fallback** covers for a dependency service — a third-party or independently-deployed service that can fail for reasons outside our control — and is important and legitimate, provided the outage turns the service's [health status](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#automatic-dependency-fallbacks-trigger-code-yellow) yellow and names the offline dependency and the fallback in use, so the maintainer is alerted to the degraded state. A **fallback within an implementation** — `try { newAlgorithm() } catch (e: Exception) { oldAlgorithm() }`, an empty result from the fast path answered by recomputing it the slow way, an old code path kept "just in case" the new one misbehaves — is a huge red flag and should generally be rejected. It almost always means the primary implementation has bugs or does not handle the edge cases it needs to, and the fallback was added so that nobody would have to find out which: the primary fails, the fallback papers over it, the tests stay green, and the expected implementation ships silently broken. The fix belongs in the primary path, with a test reproducing the case that made it fail (see [Fallbacks Are a Service-Boundary Pattern](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#fallbacks-are-a-service-boundary-pattern) and [Fix the Root Cause, Never Mask the Symptom](PHILOSOPHY.md#fix-the-root-cause-never-mask-the-symptom)).

**A silent fallback is prohibited, of either kind.** If an outage is severe enough to warrant a fallback, it must be reflected in the health status so the maintainers know; a fallback that engages with no status change — or only a log line — hides the outage, and frequently hides a broken primary implementation behind it for as long as the fallback keeps working (see [No Silent Fallbacks](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#no-silent-fallbacks) and [Never Hide a Failure](PHILOSOPHY.md#never-hide-a-failure)). A related tell is a fallback that triggers on *any* exception: the trigger must be positive evidence the dependency is unreachable or failing, never a general `catch` that would also swallow a defect in the service's own code.

Even a legitimate service fallback must arrive with [end-to-end integration tests for both code paths](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#testing-every-fallback): one with the primary working that asserts the primary served the request and the status is green, and one that simulates the primary's failure and asserts the fallback returned a correct result *and* the health status went yellow with the expected text. A reviewer facing a fallback should ask: *is the thing being fallen back from a service outside our control, or our own code? Where is the health status change when it engages? And which tests fail if the primary path breaks, or if the fallback stops reporting itself?* If the answer to the first is "our own code", the change goes back to fix the primary path; if either of the others has no answer, it goes back for the status change and the tests. A fourth question belongs beside them: *how will this fallback be exercised to completion in healthy production, and what measured signal reveals when it has atrophied?* A fallback whose PR has no answer is leaving a path to decay unobserved until the day it is needed (see [Fallbacks Atrophy Unless Exercised in Healthy Production](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#fallbacks-atrophy-unless-exercised-in-healthy-production)).

## Special-Case Exemptions from a General Rule

A diff that leaves a general rule in place and adds a branch switching it off for one named case — a path pattern, a file name, a hostname, a rule or tenant identifier, an `if (name == …)` in front of a check that applies to everything else — is a huge red flag. The exemption says the rule is false for that case, and the review has to establish *why* it is false before accepting that the answer is to stop checking. Almost always the honest reading is one of two things: the exempted input violates an invariant it was supposed to satisfy, and the fix belongs in whatever produces that input; or the rule was never true in general, and it should be replaced by one that is. Carving out the case does neither. It leaves the defect in place, it disables the only check that would have reported the next occurrence, and it is rarely the last one: a list of exemptions grows one production failure at a time, because nothing finds the next case before it fails. The cautionary case is the shared build-cache merge in BuildTestEmbedded. The merge required that two build rules writing the same cache path write identical bytes; when kompile's download records turned out to differ between rules, [BuildTestEmbedded #1084](https://github.com/CodexCoder21Organization/BuildTestEmbedded/pull/1084) exempted that one path pattern, and within a day [BuildTestEmbedded #1104](https://github.com/CodexCoder21Organization/BuildTestEmbedded/pull/1104) exempted two more for a different file that failed the same way. The first exemption's actual cause was a `Date` header written into a record that was meant to depend only on the downloaded file, fixed where it was written by [kompile-core #323](https://github.com/CodexCoder21Organization/kompile-core/pull/323) — after which the exemption protected nothing and would hide any regression of that fix. Both exemptions carried a careful written justification, which is exactly the claim this document says not to accept at face value. When a reviewer sees an exemption, the questions are: *what makes this case different, stated as a mechanism and not as "it fails otherwise"? Can that difference be removed at its source so the general rule holds? If the rule is wrong, what is the correct rule that needs no list?* An exemption that must ship to stop an outage should say so, name the source-side fix that will let it be deleted, and be tracked until it is (see [Avoid Special Cases, Optimize the General Case](PHILOSOPHY.md#avoid-special-cases-optimize-the-general-case)).

## Reaching Into Another Component's Private Files or Internal Layout

A diff whose code or tests name files that a different component manages for itself — the directory structure of its cache, the names and contents of its index or journal files, its on-disk record format, a private table — is a red flag. Those files are implementation details of the component that owns them: it is free to rename, restructure, or stop writing them in any release, and nothing in its public contract promises otherwise. Code that reads, compares, merges, or patches them has taken a dependency on a layout nobody agreed to keep, and it will break — or silently do the wrong thing — when the owner changes it. The same holds inside a single component for its own tests: a test that asserts a particular file exists under a private directory, or that an internal cache entry has particular bytes, verifies how the current implementation happens to store things, fails on a harmless refactoring, and passes on a real behavior regression that leaves the files looking the same. The cautionary case is again the BuildTestEmbedded shared-cache merge: it merges kompile's `.buildcache` directory file by file and so has to know which of kompile's internal files are deterministic, knowledge that lives as path patterns in a repository other than the one writing the files; its tests fabricate entries at those internal paths to exercise the merge. Every time kompile's cache layout changes, that code and those tests can be wrong without either repository's suite noticing. The reviewer's questions are: *who owns this file, and is its location and format part of that owner's public contract? If not, what public operation should this code be calling instead — and if none exists, should the owner provide one?* For a test, the question is *what behavior visible through the public API does this state produce, and why is the test not asserting that?* A component that needs another's state combined, exported, or validated should ask the owner to expose that as an operation, and treat the files themselves as opaque (see [Test the Public API Only](architecture/TESTING.md#test-the-public-api-only); the single-component form of this flag is [Tests Must Only Exercise the Public API](#tests-must-only-exercise-the-public-api)).

## Artificial Load and CPU Spinners in Tests

Any test that deliberately slows the machine down — a busy-loop "host CPU spinner", a background thread burning cycles, an artificial hot loop, or any synthetic load introduced to widen a timing window — is a huge red flag. It signals that the author could not reproduce a race the honest way and reached for starvation instead. Artificially loading the CPU is the wrong methodology for hunting a concurrency defect on two counts. It is *diagnostically dishonest*: starving the scheduler manufactures timeouts and stalls that need not have anything to do with the real bug, so a flake the spinner "reproduces" may be an entirely different failure, and a fix validated against it is validated against the wrong thing. And it is *unreliable*: on a host with more cores or different scheduling the added load is simply absorbed, the timing window never opens, and the underlying race goes un-surfaced — so the spinner gives false confidence exactly where it is least warranted. The reproduction that actually works exercises the *narrow* code path at a high iteration count under real concurrency, which manufactures the interleavings a timing race requires while reaching that iteration count faster through parallelism (see [Prefer Parallel Iterations Over Serial `repeat`](architecture/TESTING.md#prefer-parallel-iterations-over-serial-repeat) and [Amplify Flakes with Real Concurrency, Never Artificial Load](PHILOSOPHY.md#amplify-flakes-with-real-concurrency-never-artificial-load)). When a reviewer sees a CPU spinner or injected load in a test, the question is not "does this make the test fail?" but "what concurrent exercise of the real code path would reproduce this without lying to the scheduler?" — and the answer is almost always more iterations and more concurrency, in which case the spinner should be deleted in favor of them.

## User-Facing Message Text in a URL

Any diff in which a page renders message text taken from the request URL — a redirect that packs a whole status sentence into a query parameter (`/supervisors?deleted=Deleted%20X%20from%20the%20fleet...`) and a destination page that displays whatever that parameter contains — is a huge red flag. The query string is attacker-writable input: anyone can craft a link carrying any message they like, hand it to a victim, and the forged text renders with the full visual authority of the trusted page. The reflexive defense — "it's HTML-escaped, so there's no XSS" — misses the point: escaping stops script injection, but the vulnerability here is *content forgery*, the page vouching for words it never produced, and no amount of escaping fixes that. A reviewer who sees a handler URL-encoding prose into a redirect, or a template interpolating a query parameter into visible text, should send the change back to be restructured: render the outcome in the direct response, store a one-time flash message server-side and redirect to a clean URL, or pass only a safe selector (an ID or enumerated code) from which the destination page composes the message out of its own trusted data. Query parameters may *select* what a page shows; they must never *supply* the words it displays (see [Never Encode User-Facing Messages in URLs](architecture/GOOD_DESIGN.md#never-encode-user-facing-messages-in-urls)).

## Synchronous Network IO

Any synchronous network IO is a huge red flag. A call that blocks a thread while bytes cross the network couples the caller's health to the callee's latency, parks threads that then exhaust pools under load, and invites exactly the timeout-tuning spiral described above. Network IO should almost always be asynchronous — and the preferred shape is not "async fetch" but *subscribe and notify*: the caller obtains an identifier for the data it cares about, subscribes to it, and is notified of the current value and any subsequent updates, rather than fetching the data synchronously before proceeding, and rather than polling for it on an interval. Polling is the same red flag in a loop — it burns resources rediscovering that nothing changed and still delivers updates late. The [Observables](projects/Observables.md) library exists precisely for this pattern: reactive caching with change notification, so consumers hold a live view instead of blocking on point-in-time reads. A diff that adds a blocking network call on a request path, or a `while`/`sleep` polling loop, should be challenged to restructure around subscription.

## Locks Held Across Slow IO

**A thread lock exists for exactly one purpose: manipulating a data structure that is not safe to touch concurrently. It is never a tool for coordinating a long-running operation.** Any lock held across a remote call — an RPC, a network read or write — or across any other operation that might hang or be slow to respond (disk IO, a subprocess wait, a channel or stream open, a wait on another thread or pool) is a huge red flag, and the wider the lock's scope, the worse the flag. Threads are expensive, and a thread parked on a lock is a thread the process has paid for and cannot use; **nothing in the codebase should block a thread for a non-trivial amount of time**, and a lock held across slow work blocks not one thread but every thread that needs that lock. The failure shape has recurred countless times in this ecosystem: a lock guards some shared state, and while it is held the code performs a network operation; the connection hangs or the peer silently goes away, the holder parks inside the critical section, and every other thread needing that lock parks behind it — a single stalled connection escalates into a service-wide deadlock, with the whole system wedged on work that has nothing to do with the stuck peer (a recent production outage of exactly this shape was a run-dispatch lock held across an SSH channel open and a full read/write cycle: one hung channel and no run in the service could complete). The rule to review against is that **a lock must never be held across an RPC, network IO, or any other operation whose duration is not under the holder's control**. The critical section contains only fast, in-memory work: read or copy what the operation needs under the lock, release it, perform the operation outside, then reacquire briefly to publish the result.

Longer-lived coordination — "this run is being dispatched", "this writer owns the socket right now", "this record is mid-update" — is not expressed with a thread lock at all. It is expressed with a **lease or another data structure** that records the claim and is itself manipulated under a briefly-held lock: a leased slot with an expiry, a single-writer queue that serializes work onto a connection without parking the submitters, an in-progress marker in the state map, an actor or single-owner thread that other callers hand messages to. The thread that took the claim does its slow work holding nothing but the claim, other threads consult or contend for the claim without blocking, and a holder that crashes or hangs forfeits a lease on expiry rather than wedging a lock forever (see the [Observables](projects/Observables.md) connection-scoped lease pattern and the distributed-lock notes below). Serializing writers onto a single socket is the case most often offered as the exception to the rule, and it is not one: the lock-free shape is a per-connection outbound queue drained by one writer, and a diff that instead holds a connection-scoped lock across the write has chosen to park every other writer for as long as the peer takes to read. Where such a lock already exists in code the diff touches and is not yet restructured, it earns two mandatory checks rather than a waiver. First, **release must be guaranteed on every exit path** — a `finally`, Kotlin's `use`/`withLock`, or an equivalent construct — so that an IO exception, a cancelled coroutine, or a crashed thread can never leave the lock permanently held; a bare `lock()`/`unlock()` pair with the IO between them is the deadlock waiting for its first thrown exception. Second, **every IO operation performed under the lock must have a real timeout configured** (connect, read, and write), so a hung peer converts into a failure that releases the lock and lets the system recover, rather than an indefinite hang that no exception path can save. These timeouts are a bounded-hold safety net, not a tuning knob — their existence is no license to raise them when something is slow (see [Timeout Increases](#timeout-increases)), and a deadlock "fixed" by adding a timeout while the lock stays across the IO has mitigated the symptom, not removed the defect.

The reviewer's question for any diff that takes a lock is: *what is the longest this lock can be held, and what bounds that time?* The only acceptable answer is "the time it takes to update the structure it guards" — a bound set by the holder's own in-memory work. If the honest answer depends on a remote peer's behavior, a subprocess, a disk, or another thread — anything that can hang, stall, or vanish — the change goes back to be restructured so the slow operation happens outside the lock and any longer-lived claim is carried by a lease or data structure instead. Lock contention serializing work is also a recurring performance culprit worth the same scrutiny (see [Measure Performance, Never Speculate About It](PHILOSOPHY.md#measure-performance-never-speculate-about-it)), and blocking a thread on the network at all is its own flag (see [Synchronous Network IO](#synchronous-network-io)) — a lock held around that blocking call is the compounding move that turns one slow caller into an outage.

## Further Lock and Deadlock Considerations

The section above covers the "lock meets IO" family, but several adjacent families of lock and deadlock defects deserve the same scrutiny in review.

**Deadlock prevention by structure**

- **Lock ordering.** The classic two-lock deadlock is acquiring A-then-B on one path and B-then-A on another. A reviewable rule: acquiring a *second* lock while already holding one is itself a red flag, and where nesting is genuinely necessary, the codebase needs a single documented acquisition order. Most nested acquisitions turn out to be accidental — a locked method calling another locked method through a layer boundary.
- **Never invoke foreign code under a lock.** This generalizes the slow-IO rule: callbacks, listeners, user-supplied lambdas, and algebraic-effect handlers invoked inside a critical section can block, acquire their own locks, or re-enter the module. The lock holder no longer controls what happens under its own lock. The fix is usually to snapshot state under the lock and invoke the callback after release.
- **Hidden locks: bounded pools and channels.** A bounded thread pool, semaphore, or bounded queue *is* a lock. "Holding a lock while submitting to a bounded pool and awaiting the result" deadlocks when the pool is full of tasks waiting for that same lock. Shared bounded resources coupling unrelated work have produced real production stalls of exactly this shape. Reviewers rarely recognize a pool as a lock, which is exactly why it deserves a named flag.
- **Prefer designs with no lock at all.** The best question in review is often "why is there a lock here?" Single-writer/actor confinement, immutable snapshots swapped atomically, and message passing eliminate whole deadlock classes rather than managing them. The [Observables](projects/Observables.md) subscribe-and-notify pattern already pushes this direction.

**Mechanics that are easy to get wrong**

- **Locks must be lexically scoped.** Acquire in one method, release in another ("lock passing") means no `finally` can guarantee release. `withLock`/`use` scoping should be the default; a bare `lock()` whose `unlock()` lives elsewhere is a bug nursery.
- **Coroutines and suspension points.** Holding a thread-bound lock (`synchronized`, `ReentrantLock`) across a `suspend` call is broken — the coroutine can resume on a different thread, and `synchronized` pins virtual threads. Rule: coroutine code uses `Mutex.withLock`, and *nothing* thread-bound spans a suspension point. Also worth noting `Mutex` is non-reentrant, so a re-entrant call path self-deadlocks.
- **Document what each lock guards.** A lock with no stated guarded-field set can't be reviewed — you can't tell whether an access outside the lock is a race. Related: writes under the lock paired with reads outside it (check-then-act, double-checked publishing) are visibility bugs wearing a lock as a costume.

**Detection and testing**

- **A hang in a test must produce a thread dump, not a timeout.** Deadlock reproducers should have a watchdog that dumps all stacks (`ThreadMXBean.findDeadlockedThreads` even names the cycle) before failing — a silent CI timeout teaches nothing, in keeping with the doctrine that mitigations must never strip diagnostic signal. This could also be a production health-check primitive.
- **Deadlocks are reproducible.** The same doctrine as flakes: real concurrent callers of the narrow path at high iteration counts, then a deterministic trigger of the exact interleaving once the mechanism is named (see [Never Calibrate a Reproducer to a Machine](architecture/TESTING.md#never-calibrate-a-reproducer-to-a-machine)). "We think we fixed the deadlock" without a reproducer is a guess.

**Distributed locks**

- **A cross-process lock without a lease is a permanent wedge** — holder crashes, lock lives forever. And a lease *with* expiry but without fencing tokens silently corrupts when a stale holder wakes up and writes. Distributed locking is different enough from in-process locking that it warrants its own treatment beyond this list.

## "Loading…" Placeholder Pages

A diff that adds a page rendering "the data for this page is being loaded, the page will refresh automatically" — or any placeholder-then-auto-refresh flow — is a huge red flag. The placeholder exists because the data behind the page could not be produced fast enough, and that is almost never a fact of nature: it usually means the necessary projection is being rebuilt from scratch on demand instead of being built incrementally from only the latest relevant events, persisted across restarts, or pre-computed eagerly — the data-path defect described in [Memory That Grows with Service History](#memory-that-grows-with-service-history) and [CQRS — Materializing Projections](architecture/CQRS.md#materializing-projections), surfaced as UX. The loading page is a mitigation of that defect, and like the other mitigations in this document it hides the signal a reviewer needs: the page now *looks* functional while the underlying read path remains too slow to serve a first load. The reviewer's question is not "does the page eventually render?" but *why is the projection this page reads not already materialized at the right level?* — and the change should be sent back to fix the data path unless the author can show the computation genuinely cannot be pre-computed (a complex, arbitrary, user-supplied query is the canonical legitimate case; a dashboard over the service's own event history is not). [Resolving Slow Services](playbooks/SLOW_SERVICES.md) is the single entry point for fixing the slow read path the placeholder is papering over; see the [WUI design principles](architecture/WUI.md#design-principles) for the implementer-side statement of this rule. The same red flag covers a splash page that withholds data the page already has. Its user-facing replacement is [When Data Is Not Yet Available](architecture/GOOD_DESIGN.md#when-data-is-not-yet-available): the full page with in-place placeholders. A diff that renders an unknown value as `0` or an empty list, or that carries a chart line past its last known point, should be sent back under the same section. So should a diff that refreshes an open page by reloading it whole, or that replays a region's arrival animation on every refresh instead of animating only what changed ([Refreshing Data Already on Screen](architecture/GOOD_DESIGN.md#refreshing-data-already-on-screen)). So should a diff that gives any element its own scrollbar, such as a fixed height with `overflow: auto` or an app shell pinned to the window height with a scrolling content panel ([Only the Page Scrolls](architecture/GOOD_DESIGN.md#only-the-page-scrolls)).

## Work-in-Progress Support Files

A diff that adds files whose only purpose was to support the effort that produced it — a markdown briefing written for a delegate, an `investigations/` write-up of how a bug was diagnosed, a scratch log of commands that were run, captured test output, a review report, a findings ledger — is a red flag, and those files should be removed before the change merges. They are records of how the work was done, not part of what the repository is: they describe one point in time, go stale the moment the code moves on, and leave every future reader wondering whether they are still authoritative. The knowledge in them belongs where it will be read and kept current. The motivation and evidence for a change go in the pull request description. The state of in-flight work goes in a [handoff](projects/Handoff.md). A lasting insight goes into the component's README or the relevant architecture document here. And the regression it uncovered is captured as a test, not as prose describing one. Such files belong in a repository only when a user has explicitly asked for them to be committed, which is uncommon. A reviewer who sees one should ask for it to be dropped from the diff and its useful content moved to the right home. (For what such a briefing should contain while it is in use, see [Delegating Engineering Work](playbooks/DELEGATION_BRIEFS.md).)
