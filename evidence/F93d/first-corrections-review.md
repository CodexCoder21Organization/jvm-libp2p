## Test-comprehensiveness pass

I read the full 390-line `PlainNettyTransport.kt`, 131-line `ParentCloseOwnershipTest.kt`, and 375-line `ConnectionCloseRetryTest.kt` from the product checkout, then compared their full commit diff.

- The product change at `PlainNettyTransport.kt:234–238` moves `readiness.completeExceptionally(...)` until after the listener/channel close operations, group-shutdown continuation, and completion handler have been installed. This matches the supplied mechanism: readiness completion can synchronously drain a reentrant `close().get()` callback, so cleanup must already be scheduled. The monitor is released before the readiness callback runs.
- In `ParentCloseOwnershipTest`, the body is unchanged. Cleanup still removes the handler, physically closes the raw channel, and uses the original 10-second bounds. It now unwraps `client.stop()` and checks `assertSame(failure, reported)` at lines 122–124, then awaits `server.stop()` separately with 10 seconds at lines 125–126.
- In `ConnectionCloseRetryTest`, body assertions are unchanged except for the two Addendum-approved post-success assertions at lines 134 and 224. Each checks that `connection.transport().close()` still reports the same injected failure after `retryClose()` and `closeFuture()` complete.
- The `withRetryConnection` cleanup calls `parent.transport().close()` through the public API and unwraps its result (lines 347–357). In the two affected cases, the body has already asserted that this transport result is the injected `failure` object (line 128 and line 215); the new post-success assertions preserve that same identity after retry. Cleanup then checks that `client.stop()` has the same unwrapped root object, and `server.stop()` is awaited in `finally`. This verifies the transitive identity required by A1. In unaffected cases, a successful transport close takes the success branch.
- There is one test-scope caveat: the `withRetryConnection` helper now treats any non-null `parent.transport().close()` error as an expected client-stop error for every test using that fixture. In the two A1 cases, the bodies establish the injected identity, so the new check is grounded. For other fixture callers, an unexpected transport-close error would pass cleanup if `client.stop()` repeats it. That is a broader accepted failure outcome than the previous `allOf(...).get(10s)` success assertion; it should be kept in view under `CODE_REVIEW.md` “Weakening an Existing Test.” I made no changes because A1 binds the allowed edit and the manager owns any follow-up ruling.
- The success branch also waits sequentially: `client.stop().get(10s)` at line 351, then `server.stop().get(10s)` in `finally` at line 360. The prior `allOf(client.stop(), server.stop()).get(10s)` started both stops together and bounded the combined wait to 10 seconds. The new success path can take up to 20 seconds. A1 specifies the separate 10-second awaits for the expected-failure path; it does not require serializing the unaffected success path. This is a concrete timeout-scope difference to decide against `CODE_REVIEW.md` “Timeout Increases.”
- The manager reports the existing Noise reproducer failed 30/30 at `f6326b65` and passed 30/30 on `develop`; the candidate result is still queued. That is strong baseline evidence for the readiness fix, but the candidate green is not yet confirmed. This review did not run it.

The tests use real loopback hosts, public `Transport.close()` / host-stop behavior, injected Netty close failures, and real concurrent callers. The new assertions do not add mocks, reflection, or internal visibility. The existing direct Netty channel operation remains cleanup already present before this commit.
