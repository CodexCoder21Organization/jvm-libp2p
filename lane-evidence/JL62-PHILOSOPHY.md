# Engineering Philosophy

This document collects the cross-cutting engineering philosophies that guide how everything in this ecosystem is built. Where the [standard layered architecture](architecture/STANDARD_LAYERED_ARCHITECTURE.md) describes *how a service is structured* — its [Api](architecture/API.md), [Embedded](architecture/EMBEDDED.md), [ServiceServer](architecture/SERVICE_SERVER.md), and the rest — this document describes *how we work*: the values that decide what counts as a real fix, an honest test, and finished work. Several of these principles have a fuller, more practical treatment elsewhere (especially in [Testing](architecture/TESTING.md) and [State Management](architecture/STATE_MANAGEMENT.md)); those documents are linked inline, and this page is the place where the principles behind them are named and explained. For the concrete, diff-level patterns that should raise a reviewer's eyebrows — reflection, timeout increases, resource increases, "the host is overloaded" claims, unmeasured performance claims, artificial test load and CPU spinners, missing test coverage, synchronous network IO, big-bang migration diffs — see the companion [Code Review Red Flags](CODE_REVIEW.md).

## Fix the Root Cause, Never Mask the Symptom

When code times out, fails intermittently, or runs slowly, that is a *symptom* — of a deadlock, a race condition, an unbounded loop or recursion, a resource leak, an inefficient algorithm, or a dependency that has gone unresponsive. The instinct to raise a timeout, lower a stress test's iteration count, drop in a `sleep`, or wrap the call in a retry loop is a reliable signal that the real cause has not yet been found, because none of those changes touch the underlying defect — they only make the failure take longer to surface while quietly eroding the very thresholds that exist to catch problems before users do. A timeout that "needs" to be increased is a bug that has not yet been understood. The only acceptable response is to investigate until the cause is known, fix that cause, and confirm the code now completes comfortably within the *original* limits. (See [Symptoms vs. Causes, Generally](architecture/TESTING.md#symptoms-vs-causes-generally) and the [OOM case study](architecture/TESTING.md#ooms-are-symptoms-of-memory-leaks-not-bugs-to-be-handled) for this principle applied to memory leaks.)

## Never Hide a Failure

A failing test is doing its job: it has caught something. The correct response is always to fix the code it caught — never to silence the signal. Deleting the test, marking it disabled, skipping it in CI, swallowing the exception in a `try`/`catch`, weakening an assertion (for instance from `assertEquals` to `assertNotNull`), or excluding it from the build all destroy information about a real defect while manufacturing the false comfort of a green build. A missing dependency or an incomplete environment is likewise a reason for a test to *fail loudly*, never a license to skip it with an assumption that silently passes without verifying anything — a skipped test reads as a pass but proves nothing. If a test genuinely encodes wrong behavior, that is a deliberate, explicit change to discuss and make on purpose, not something to paper over. (See [Never Skip Tests](architecture/TESTING.md#never-skip-tests).)

## Reproduce a Bug Before You Fix It

Every bug fix begins with a failing test that reproduces the bug — written *before* the fix and confirmed to fail *because* of the bug. This discipline forces a genuine understanding of why the bug exists and what the correct behavior should be before a single line of implementation changes; it proves the fix addresses the actual defect rather than something adjacent to it; and it leaves behind a permanent regression guard so the same bug cannot silently return. A fix without a reproducing test is a guess, and a guess that happens to work is indistinguishable from one that doesn't. This is **[test-driven development (TDD)](architecture/TESTING.md#test-driven-development)**, and it is the default way of working in this ecosystem for new features as much as for bugs — write the test that describes the behavior, watch it fail, then make it pass. (See [Test-Driven Development](architecture/TESTING.md#test-driven-development) and the [Bug Fix Testing Workflow](architecture/TESTING.md#bug-fix-testing-workflow); when a fix has already shipped and the production symptom is still there, start from the playbook [When a Fix Does Not Fix Production](playbooks/FIX_DID_NOT_HOLD.md).)

## Amplify Flakes with Real Concurrency, Never Artificial Load

A flaky test reproduces reliably when you exercise the exact narrow code path enough times, under enough genuine concurrency, to manufacture the interleaving the race needs — never by artificially slowing the machine down. A CPU spinner, a busy-loop thread, or any synthetic load introduced to "widen the timing window" fails twice over: it produces timeouts and stalls unrelated to the defect, so a fix validated against it is validated against the wrong failure, and it is an unreliable amplifier anyway, absorbed harmlessly on a host with more cores. Real concurrency against the true code path does double duty — it exercises the shared state where the race actually lives and reaches a high iteration count fast — and if reproduction still eludes you, the answer is more iterations and more real concurrency, never a heavier load on the box. Amplification is a discovery tool: once diagnosis names the exact condition the code mishandles, the reproducer graduates to a deterministic trigger that forces that condition directly, because a reproducer whose reliability varies with the machine is calibrated to a host rather than to the contract. This applies whenever a test fails intermittently, whether in CI, in the merge queue, or locally. The methods are in [Stress Testing for Flake Reproduction](architecture/TESTING.md#stress-testing-for-flake-reproduction), [Prefer Parallel Iterations Over Serial `repeat`](architecture/TESTING.md#prefer-parallel-iterations-over-serial-repeat), and [Never Calibrate a Reproducer to a Machine](architecture/TESTING.md#never-calibrate-a-reproducer-to-a-machine).

## Fix Flakes and Infrastructure Pain Along the Way, Never Ignore Them

A flake met on the way to something else is not an interruption to route around; it is a defect that has just announced itself, and the moment it is noticed is the cheapest moment there will ever be to fix it. The flake is amplified until it reproduces reliably — by [real concurrency, never artificial load](#amplify-flakes-with-real-concurrency-never-artificial-load) — its root cause is found, and it is fixed, in the same pass as the work that surfaced it. Re-running the job until it goes green, marking the test, or noting the flake "for later" all leave the defect in place and teach it to the next engineer as background noise; the [flaky test policy](architecture/TESTING.md#flaky-test-policy) forbids every one of them. This work must not become a side quest that stalls the main task, and it must not be dropped either; the way to satisfy both is **delegation with ownership**. A flake is usually independent of the change that tripped over it, so the engineer or agent who meets it hands the fix off at once — to a separate agent, a separate engineer, or a separate lane of their own work — with its own reproducer, its own fix, and its own pull request, and then carries on with the original task uninterrupted. The flake does not widen the original change's landing bar: the change lands on its own first-attempt-clean required checks and tests of the changed behavior and its clean reviews, while an unrelated flake found only in a separate, wider test register races it as a separate pull request; sequence the two only when either inherently depends on the other (the change needs a version the fix publishes, or the fix needs an API the change introduces), without waiving a failed required check or retrying it unchanged. The handoff names an owner: someone is responsible for driving that fix to landed, and the main task's status report says who, so a flake never ends up noticed by everyone and owned by no one. Independent flake fixes against the same repository are **raced** rather than sequenced: each is driven to green and enqueued on its own, whichever lands first lands, and the others take a mechanical rebase. The one situation to watch for is **mutual blocking**: several independent flakes exist at once, and every pull request — each flake fix included — is evicted by the flakes it does not fix, so nothing can land on its own. The tell is a merge drought in a repository where several green-on-branch fixes are each failing in the queue on a *different* test. When that is what is happening, the fixes are deliberately **bundled** into one pull request so the queue sees a head on which none of the known flakes fire; bundling is the exception that exists for exactly this deadlock, not a reason to batch unrelated work, and the bundle's description names each flake it carries and where it was observed. The same pattern seen from the other side — one failure that rotates among victims across runs — is a single shared defect rather than many unlucky tests, and gets one fix rather than many.

The same rule covers every other pain point met on the way: slow or broken infrastructure, a tool that fails in a surprising way, a service that answers in thirty seconds instead of one, a build that needs three re-runs to pass, a document that sent you down the wrong path — and, most often of all, a build or CI run that is simply slow. Each is a continuous tax in the ordinary case — paid again on every job by every engineer and every agent, invisibly, because everyone routes around it the same way — and in the worst case it is what makes progress grind to a halt, when the taxes compound until nothing lands at all. So friction is identified and fixed along the way exactly as a flake is — delegated at once to an owner who drives the fix to landed while the main task continues in parallel, never left as an unowned note and never allowed to pull the main task off course: [shared infrastructure simply must work](#performance-and-reliability-are-features), "it's just the environment" is a hypothesis to disprove rather than a conclusion to reach, and the fix goes at the layer that owns the defect — the [slow service](playbooks/SLOW_SERVICES.md), the [systemically failing CI](playbooks/CI_SYSTEMIC_FAILURES.md), the upstream library, the stale instruction — never into a local workaround that hides the tax from the next person. When the slowness is a project's own size — a suite that takes most of an hour because the project has quietly become several — the fix is the one in [Keep Projects Small](#keep-projects-small-clear-contracts-and-tests-that-enforce-them): split it, so that each change runs only the tests that concern it. When the fix genuinely cannot be made in the same pass, the friction is still recorded the moment it is understood, with what was attempted, the exact failure, the impact, the workaround, and the durable fix it needs, in the [PlanRepository challenges record](https://github.com/CodexCoder21Organization/PlanRepository/tree/main/challenges), so that it is fixed once instead of rediscovered by everyone who follows. A workaround that nobody wrote down is a tax that has just been made permanent.

## Test End-to-End Against Real Dependencies

Tests verify a component's public API against *real* instances of its dependencies, not against mocks. When a test needs a server, it starts a real one; when it needs storage, it uses an in-memory implementation of the real interface. A mock only confirms that the code called the methods the test author expected — it cannot catch the protocol mismatches, integration bugs, and behavioral regressions that appear when the real parts are wired together, which are precisely the failures worth catching. Tests should also exercise only the public API, so that refactoring an implementation never breaks a test as long as observable behavior is preserved, and they should be [hermetically sealed](architecture/TESTING.md#tests-must-be-hermetically-sealed) and side-effect-free, preferring in-memory filesystems and databases to real ones so that the same test yields the same result on every machine, in any order, run alone or alongside the whole suite. (See [End-to-End Tests, Not Mocks](architecture/TESTING.md#end-to-end-tests-not-mocks) and [Test the Public API Only](architecture/TESTING.md#test-the-public-api-only).)

## Tests MUST Be Comprehensive: A Bug Caught Downstream Is a Suite Failure Upstream

A test suite exists to find every bug before anyone else does, and it is judged by where bugs are actually found. Two events are therefore not bad luck but **abject failures of a test suite**, and each is read the same way. When a dependee upgrades a dependency and a failure appears, the dependency's own suite should have caught it; that it was caught by a consumer instead means the suite is woefully inadequate — and not only at the one spot that failed, since a suite that missed this has almost certainly missed its neighbours. When a production deployment is rolled back, the same verdict applies: no problem should ever reach the point of a production deployment, so a rollback is proof that the suite let one through. In both cases the response is never a single regression test for the one bug. It is a **comprehensive check of the whole suite for other gaps** — every dimension in [Are the Tests Comprehensive?](architecture/TESTING.md#ultrathink-are-the-tests-comprehensive) walked again against the code the failure exposed, with each gap closed by a test that fails first. Comprehensive means at scale as well as in kind: all code is tested under [extreme conditions](architecture/TESTING.md#extreme-condition-testing-load-fuzzing-failure-injection-and-chaos) — saturating load, oversized inputs, injected failures, degraded networks — and is robust to race conditions and to scale, because a defect that appears only at production volume or under genuine concurrency is still a defect the suite was supposed to find. This applies to every project, and most sharply to the ones others depend on, whose suites should also exercise their [real downstream consumers](architecture/TESTING.md#cross-repository-integration-testing) so that "did my change break anyone who uses me?" is answered before the change ships rather than by the consumer who upgrades. The reviewer's side is [A Dearth of Test Coverage](CODE_REVIEW.md#a-dearth-of-test-coverage).

## Fix Bugs Upstream, Never Patch Around Them Downstream

When a leak, race, or correctness bug surfaces in a consuming service but originates in an upstream library, the fix belongs in the library — not in the consumer. A downstream workaround (a `try`/`catch` that swallows the symptom, a local fork or shaded copy, an added retry loop, a disabled feature) hides the bug from every other consumer of that library, hardens into permanent technical debt, and turns actively wrong the moment the library is updated. The correct path reproduces the symptom with a failing test in the consumer, isolates it with a failing test in the library, fixes the library at its source, publishes a new version, and bumps the dependency — closing the loop so the consumer's original test proves the upstream fix resolved the user-visible problem. Fixing upstream repairs the defect once for every consumer and keeps the dependency relationship honest.

## Performance and Reliability Are Features

Code is expected to be fast and reliable by default, and slowness or flakiness is treated as a defect to be diagnosed rather than a fact of life to be accommodated. Globally shared infrastructure — the build system, the P2P network — simply must work, so "it's just the environment" is a hypothesis to disprove with forensic analysis (heap dumps, thread dumps, connection state, protocol traces), not a conclusion to reach by default. The two most seductive forms of that excuse deserve naming, because both are almost always wrong: **"the JVM needs more memory"** (it doesn't — an `OutOfMemoryError` is a leak or a payload materialized in heap instead of streamed; take a heap dump and find what is actually retained, never raise `-Xmx`) and **"the host is over capacity"** (it isn't — the swarms are small and the work is light; an apparently overloaded box is the symptom of non-linear gossip, a thread or memory leak, or a JVM over-allocating heap until the OS swaps). When something is slow, the answer is to find and remove the cost — a connection leak, an allocation storm, a full re-serialization on every request, a stalled peer with an unbounded write backlog — never to wait it out with a longer timeout, an extra retry, an added delay, more heap, or a bigger machine. Performance and reliability are properties engineered into the system, not knobs to be relaxed when they become inconvenient. The same discipline extends to the tests that guard these properties: a test's verdict must never depend on which machine runs it, so bounds are generous by construction and complexity guards discriminate on an algorithm's shape, never a host's speed. (See [OOMs Are Symptoms of Memory Leaks](architecture/TESTING.md#ooms-are-symptoms-of-memory-leaks-not-bugs-to-be-handled), [The Host Is Almost Never Over Capacity](architecture/TESTING.md#the-host-is-almost-never-over-capacity), and [Test Verdicts Must Be Hardware-Independent](architecture/TESTING.md#test-verdicts-must-be-hardware-independent).)

## Measure Performance, Never Speculate About It

Performance problems are uniquely resistant to being reasoned about from the source: the bottleneck is rarely where a careful reading of the code predicts it will be. So **every claim about the cause of a performance problem must be backed by a concrete profile taken from the running production system** — a heap dump for what is actually retained, a thread dump for what the code is actually doing — and a root-cause explanation supported only by reading the code is a hypothesis, wrong far more often than intuition admits; be most skeptical of your own. The profile names the mechanism, the fix removes that mechanism, and the same measurement proves the fix moved the number it claimed to move — re-checked after the problem's recurrence period, since a restart alone makes any accumulation bug look fixed for a while. The fix is systemic, never a cap: a concurrency cap, an admission throttle, or more heap in front of an unprofiled cost hides the defect and strips the very signal needed to diagnose it. This applies whenever something is slow, saturated, or growing — a page, a service, a test, a coordinator. The tool kit, the usual suspects, and the verification procedure are in [Resolving Slow Services](playbooks/SLOW_SERVICES.md); the reviewer's side is [Unmeasured Performance Claims](CODE_REVIEW.md#unmeasured-performance-claims).

## A Refuted Hypothesis Is a Successful Outcome

An investigation exists to determine what is true, not to confirm what was suspected. When work is framed as "find the shared mechanism behind these failures," whoever does that work — a person or a delegated agent — is being quietly rewarded for finding the implied mechanism, and an investigator optimizing to complete the task will keep hunting for it long after the evidence has stopped supporting it. So give every investigation an explicit criterion under which the premise can be *positively refuted*, and treat an evidence-backed refutation as a first-class successful result: unless the stated expectation explicitly says otherwise, "the premise is wrong, and here is the evidence" is an acceptable — often the most valuable — outcome, because it redirects the plan before more work is spent on the wrong theory. The same license flows down through delegation: a delegate should be encouraged to contradict the premise it was handed when the evidence points elsewhere, and a delegate that declines an instruction with better evidence is the system working, not a failure to comply. (The playbook [Delegating Engineering Work](playbooks/DELEGATION_BRIEFS.md) covers how to write that license, and the rest of a brief, down.) Pre-registered success criteria — decided before any results exist — keep this honest in both directions: they stop the investigator from renegotiating failure into success after the fact, and they stop the requester from dismissing an unwelcome refutation as noise. (See [Measure Performance, Never Speculate About It](#measure-performance-never-speculate-about-it) for the evidence discipline, and [Understand Before Fixing](architecture/TESTING.md#understand-before-fixing) for the same rule applied to flake hypotheses.)

## Avoid Special Cases, Optimize the General Case

When a path is slow, the tempting shortcut is to detect the *easy* case and route it around the general machinery — most commonly, sniffing whether a connection's peer is `localhost` or a loopback address and hand-tuning a fast path just for it while every other connection pays full price. This is the wrong instinct. A special case is code that must be written, tested, documented, and kept correct forever, and it forks every future change in two: the optimization reaches a privileged few, while the path most traffic actually travels — connections between distinct hosts across the mesh — stays slow. The right move is to make the *general* case fast, so that a loopback connection is quick simply because *every* connection is quick and the loopback peer is nothing more than the trivial instance of the same well-optimized path. Optimizing the general case is more maintainable (one path to reason about, not two), it hands the benefit to every caller rather than a lucky subset, and it removes the standing hazard that the fast path and the slow path silently drift out of agreement. A special case earns its place only when the general and special cases are genuinely, irreducibly different in behavior — never as a substitute for making the common path fast. This is the design-side complement of treating [performance and reliability as features](#performance-and-reliability-are-features), and it is exactly what the [direct-mesh-first connection model](architecture/STANDARD_LAYERED_ARCHITECTURE.md#connection-model-direct-mesh-first-relay-only-as-a-fallback) already embodies: every peer rides one uniformly-optimized connection instead of a lattice of purpose-built shortcuts, so the system is fast for everyone by construction.

## Migrate Heavily-Used Contracts Gracefully, Break Unused Ones Freely

The care a contract change deserves is proportional to how heavily the contract is used in production. A brand-new or lightly used service should just make the breaking change — migration machinery there buys nothing — while a service the fleet depends on (anything touching buildtest or NetLab affects the health of every build) must never break an existing function's contract. A change to a function's *observable behaviour* is a contract change even when the signature is untouched: truncating a result that was previously complete breaks callers as surely as renaming the method, and recognizing that is the author's job, never the reviewer's. The graceful path is deprecate-and-add: the new function arrives beside the old one, the old one keeps its exact contract until every deployed consumer has moved, and the client dependency speaks both shapes so server and client roll out independently. The same never-break shape governs a change of which *system* fills a production role — a parallel run with only the old system authoritative, a flip once they demonstrably agree, deletion last. The one place such a fallback is routinely justified is the decoupled server–client boundary, where version skew is permanent; in embedded, in-process code a fallback only hides defects in the new implementation and should generally be rejected in review, the migration-flavoured version of [masking a symptom](#fix-the-root-cause-never-mask-the-symptom). This applies to any change a deployed consumer can observe. The full policy — dual-path clients, the migration matrix, parallel-run cutovers — is [Graceful Migrations & Fallbacks](architecture/GRACEFUL_MIGRATION_FALLBACKS.md).

## Plan Migrations to the End, Land Them One Small Step at a Time

A migration — splitting a monolith into published modules, moving a service onto a new storage engine, replacing one system with another, retiring a contract fleet-wide — is planned with its ultimate destination in view, and the *whole* plan is written down before the first step lands: the end state, every step between here and there, the order and why, and what each step leaves working. That plan is an architecture document committed to the repository being migrated, or a [PlanRepository](https://github.com/CodexCoder21Organization/PlanRepository) workstream when the migration spans repositories — the [repository is the source of truth](#the-repository-is-the-source-of-truth) for where we are going just as it is for what exists. The *implementation*, however, is never the plan executed in one move: it is a sequence of bite-size changes, each merged on its own, each leaving `main` fully working and tested, each moving the code measurably closer to the documented end state. The coordinated big-bang migration — one enormous diff, or a set of pull requests that only work once they all land together — is what this forbids: it cannot be reviewed as a unit, cannot be reverted except wholesale, drifts from `main` while it waits, and when it breaks something the breakage has as many candidate causes as the migration had steps. The two halves hold each other up: without the plan, small steps wander and stall half-done; without small steps, the plan becomes a risk the size of the whole migration landing at once. This applies to any change too big for one pull request. How to write the plan, sequence the steps, and recognise a big bang in disguise is in [Planning and Landing a Migration](playbooks/MIGRATIONS.md); the reviewer's side is [Migration Steps Without a Plan, and Big-Bang Migration Diffs](CODE_REVIEW.md#migration-steps-without-a-plan-and-big-bang-migration-diffs).

## Errors Should Explain Themselves

An error message exists so that whoever reads it understands what went wrong and what to do about it. A good message states what was expected, what the actual value was, and why that value was wrong — `--test path must be a directory or a .kts file, but the provided path (/home/user/workspace/fav5) does not exist` rather than a bare `--test path must be a directory or a .kts file`. The reader should never have to open a debugger or read the source to recover information the program already had at the moment it failed. The same standard applies to anything user-facing: surface enough detail to fully understand and resolve the problem, and when asserting on errors in tests, assert against the *full* text so the quality of the message is itself protected.

## The Repository Is the Source of Truth

Work that exists only in a working directory, or only on a running server, is an operational risk: deployed code drifts from what is recorded, fixes live in places they can be lost, and no one can review or reason about what actually shipped. The risk starts long before the work is finished: local working trees are volatile, so in-flight work is checkpointed to a remote branch from the *first* meaningful milestone — a reliably-failing reproducer, a passing test, a completed sub-analysis — not gathered up in one push at the end. The running test is: *if this effort died right now, could a fresh one resume from the last checkpoint without redoing any finished work?* Completed work is committed to a branch, covered by comprehensive end-to-end tests, and opened as a pull request whose CI is driven all the way to green — and merged only with explicit human approval, never automatically. The repository, not a developer's machine and not a live container, is the authoritative record of what the system is; every other copy is derived from it and must be reconciled back to it. What the repository records is the system itself: the briefings, investigation notes, and scratch output that supported an effort do not become part of that record, and are not committed unless a user explicitly asks for them (see [Work-in-Progress Support Files](CODE_REVIEW.md#work-in-progress-support-files)). (This mirrors the broader [state management](architecture/STATE_MANAGEMENT.md) principle that derived state is never edited in place — only rebuilt from its authoritative source.)

## Keep Projects Small: Clear Contracts, and Tests That Enforce Them

A project should be small, should state its contract — what it owns, what it guarantees about ordering and failure, what its public surface is — and should carry a test suite that enforces that contract through the public API alone. Projects do not stay that way on their own: the common history is a module that grows, fix by fix, until it is unsustainable — one package of a hundred thousand lines, a service class nobody can hold in their head, thousands of tests that take most of an hour across many CI shards, and review rounds that keep rediscovering a cross-boundary rule that nothing states as a contract. The signal to act on is the **test suite's running time** — a slow suite is the commonest form of the [friction tax](#fix-flakes-and-infrastructure-pain-along-the-way-never-ignore-them), paid on every change by everyone: when the unit tests of one project take a long time to run, that is the moment to step back and ask whether the project is really several — and to split the independently specifiable parts into sub-projects, each in its own repository with its own stated contract and its own comprehensive suite that enforces it, published as an artifact the main project depends on. The main project then composes those published modules behind their contracts, and *its* suite becomes the integration layer, testing the final assembly end-to-end against the [real sub-projects](architecture/TESTING.md#cross-repository-integration-testing) rather than re-testing their internals. The payoff is rapid iteration: a change to one sub-project is a pull request on that sub-project, verified by running only its own relevant tests in a minute rather than the whole assembly's in an hour, with the integration suite confirming the composition when the dependency is bumped. The same instinct that says [extract a submodule instead of raising a helper's visibility](architecture/TESTING.md#extract-submodules-instead-of-increasing-visibility) applies at project scale, and a split of this kind is a migration — plan the module boundaries and their order to the end, then [land one extraction at a time](#plan-migrations-to-the-end-land-them-one-small-step-at-a-time) with no behaviour change inside an extraction; the [BuildTestEmbedded modularization](https://github.com/CodexCoder21Organization/PlanRepository/blob/main/workstreams/BuildTestEmbeddedModularization.md) is this principle being applied to exactly the history above. The [Splitting a Project into Sub-Projects](playbooks/SPLITTING_PROJECTS.md) playbook is the start-here guide for doing the split: which seams qualify, how small the API must be, and how the plan and the extractions are sequenced. This is the codebase-side twin of [Prefer Cattle Over Pets](#prefer-cattle-over-pets-isolated-services-that-outlive-their-manager): small isolated units with stated boundaries are what keep both a running fleet and a growing codebase manageable.

## Prefer Cattle Over Pets: Isolated Services That Outlive Their Manager

Every service is an independent, disposable unit rather than a hand-tended pet — it can scale to zero, cold-start on demand, and be replaced wholesale instead of nursed back to health. A coordinator may manage many such services at once (distributing updates, checking health, orchestrating deploys), but its absence must never take a service down: with the manager gone, each service is still completely operational. That isolation is exactly what makes the system manageable at scale — one service's load can never starve another (a property that is [enforced by per-app resource caps](architecture/ISOLATION.md), not assumed), dependencies are upgraded one service at a time instead of in a fragile big-bang, a failed or compromised service has a contained blast radius, a service can be relocated geographically without disturbing its neighbours, and a full backup is small enough to verify offline by restoring it on a laptop with the network unplugged and confirming exactly what was preserved. The costs are real and worth naming plainly: more independent things to run, more addresses to configure, and sweeping cross-service changes that are harder than a single central edit — trade-offs we accept because isolation buys a resilience a shared monolith cannot. The [ephemeral ServiceServer and WUI](architecture/STANDARD_LAYERED_ARCHITECTURE.md#serviceserver) already embody this: they hold no authoritative state of their own, so losing one loses nothing that was not already persisted in a dependency service.

## No Central Service Is a Single Point of Failure

A central service — a shared build service, a hosted index, a coordinator — earns its place by making the fleet faster or simpler, never by becoming the thing the fleet cannot work without. Every consumer of a central service keeps an alternative that is [as uncorrelated with it as possible](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#choose-fallbacks-uncorrelated-with-their-primary) — ideally a completely local implementation — and engages it automatically, under the visibility rules of [Graceful Migrations & Fallbacks](architecture/GRACEFUL_MIGRATION_FALLBACKS.md): a dependency-outage fallback that turns the consumer's health status yellow, or, where the central service supplies speed rather than truth, a [race between the central service and the local alternative](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#racing-a-central-service-against-a-local-fallback-ci-builds) in which whichever finishes first wins and a failed side is a loud warning rather than a failed job. CI is the canonical case: a GitHub runner invoking kompile-cli races its own local build against the central `url://buildtest/` service, takes the remote result in the common path because it is faster, and completes on the runner alone whenever the central service is offline for any reason. The test for any central dependency is the drill in [Verify Resilience by Taking Dependencies Offline on Purpose](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#verify-resilience-by-taking-dependencies-offline-on-purpose): switch it off and nothing stops — things get slower, status pages go yellow, and the outage is impossible to miss, but no build, merge, or request is blocked. This is the operational complement of [Decentralized by Default](#decentralized-by-default-anyone-can-run-it-themselves): that principle says no service may require a central provider in order to exist; this one says no running fleet may require one in order to keep working.

## Guard Against Atrophy: Every Code Path Keeps Running in Healthy Production

A code path that runs only when something is broken is a path that will be broken when something finally runs it. Fallbacks, the losing side of a race, backup and restore procedures, crash-recovery and cold-start paths, a deprecated function kept alive for a migration — all of them atrophy while the healthy path carries the traffic: the runner image moves on, a dependency drifts, a quota changes, the suite grows past the backup's timeout, and nothing notices because nothing is looking. The failure is silent in exactly the way [Never Hide a Failure](#never-hide-a-failure) forbids, and it is discovered at the worst possible moment, when the primary is down and the backup is all that is left. Tests are necessary but not sufficient, because atrophy comes from the production environment changing underneath an unchanged path. So **every code path is continually exercised in healthy production**, to completion, against real inputs and the real current infrastructure, and its result and duration are measured against a pre-registered threshold whose breach is a visible yellow signal and a defect to fix, never a limit to raise. The exercise budget is a deliberate choice at each of three scales — a share of real traffic that always takes the alternate path, an operator's switch that forces the fallback on demand, and a chaos drill that takes the primary offline — and the only unacceptable choice is zero, the choice made by default whenever nobody makes one. This applies to any path that exists for the case where something else has failed. How the three exercises work, and why a parallel run beats a standby, are in [Fallbacks Atrophy Unless Exercised in Healthy Production](architecture/GRACEFUL_MIGRATION_FALLBACKS.md#fallbacks-atrophy-unless-exercised-in-healthy-production).

## Contain the Blast Radius: A Bug in One Module Never Starves Another

Isolation that is merely designed is not isolation; it has to be enforced. Two services can be perfectly independent on paper and still share a machine, and the moment one of them leaks memory, spins a CPU, or fills the disk, its neighbours go down with it — not because of anything they did, but because nothing stopped the faulty one from taking everything. So every app, service, and module is allocated an explicit **cap on each shared resource it can consume** — CPU, memory, disk, and the metered budgets that [rate limits](architecture/RATE_LIMITS.md) govern — enforced by the layer that hosts it rather than trusted to the app's own good behaviour. Two rules keep this consistent with the rest of this document: a cap protects the neighbours and is never a remedy for the hog, so hitting one is a loud defect in the capped unit and never evidence that "the host was overloaded"; and a cap is sized from measured healthy usage and never raised because it was hit, which is the [resource-increase red flag](CODE_REVIEW.md#resource-increases). This applies to anything that shares a machine with anything else — a deployed service, a forked test JVM, client bytecode, a metered caller. Which layer enforces which cap, how caps are sized and attached, and how the containment is verified are in [Isolation](architecture/ISOLATION.md). This is what turns the [cattle-over-pets](#prefer-cattle-over-pets-isolated-services-that-outlive-their-manager) claim that one service's load can never starve another from a design intention into an enforced property.

## Decentralized by Default: Anyone Can Run It Themselves

A service should not require a central provider in order to exist. The same Api is available along a single [deployment spectrum](architecture/STANDARD_LAYERED_ARCHITECTURE.md#deployment-spectrum-embeddable-library-subservice-and-hosted-service) — as an in-process **Embeddable Library** with no IPC, as a **Subservice** the user self-hosts on their own hardware, or as a fully managed **Hosted Service** — and any consumer can be configured to reach each of its dependencies locally or remotely, so a parent can spin up a child service and keep full control over what that child is allowed to access (for instance hosting its own authentication module in-process rather than consulting a central authority). The model to aim for is Ubiquiti Unifi rather than Verkada: run it yourself, offline if you like, holding your own [W3Wallet](projects/W3Wallet.md) keys, and connect to a vendor's coordinator only for management and updates if and when you want them — never as a precondition for the service working at all. Bringing a service up requires only something on the port that can find and securely launch its code and act under the right identity, which [UrlResolver](projects/UrlResolver.md) bytecode fetch, the [SJVM sandbox](architecture/STANDARD_LAYERED_ARCHITECTURE.md#sandboxed-execution-and-security), and [ContainerNursery](projects/ContainerNursery.md) cold-start already provide. The honest limits: genuinely shared, deduplicated datasets are harder here — needing sharding for availability and decentralized access control for mutable data — and a few inherently privileged operations still require a remote authority; we treat these as known trade-offs of sovereignty, not reasons to recentralize by default. The fully decentralized, everyone-runs-their-own end of this spectrum is an aspirational direction tracked in [the plan](https://github.com/CodexCoder21Organization/PlanRepository/blob/main/BRAINSTORMS.md).
